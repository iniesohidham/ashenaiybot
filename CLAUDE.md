**Known environment gotchas hit while building this** (re-verify if they seem to not apply anymore):
- `pnpm` isn't preinstalled; `corepack enable` fails with `EACCES` in some sandboxes — use `npx pnpm@<version>` as a workaround, or fix corepack's permissions.
- Docker CLI may be present with **no running daemon** and no Desktop app — `colima start` (via `brew install colima`) is a working fallback; afterwards use `docker-compose` (v1 standalone binary), not `docker compose` (v2 plugin isn't installed).
- If you switch Docker contexts (e.g. Desktop → colima), `~/.docker/config.json`'s stale `credsStore` (e.g. `"desktop"`) breaks every pull with a `docker-credential-desktop not found` error — remove that key if `auths` is empty.
- The npm registry connection from this network is slow/flaky (frequent `ECONNRESET`, likely the same Iran-access risk noted in the PRD's own §9) — give installs generous timeouts and prefer `run_in_background` with direct (non-`tail`-piped) logging so progress is actually visible.
- A local HTTP(S) proxy (`http_proxy`/`https_proxy` env vars) is active and intercepts even `curl`/local-server requests to `127.0.0.1` — use `--noproxy '*'` when curling a locally-running dev server, or you'll see confusing `502` responses that look like a server bug.
- Manually running the bot against live Telegram in this sandbox needs the same proxy: `curl`/`fetch` with `NODE_USE_ENV_PROXY=1` reach `api.telegram.org` fine, but grammY's Node fetch shim is `node-fetch`, not the global `fetch` — it ignores that env var entirely and `bot.start()` just hangs forever on `getMe()` with **no error at all**, which looks identical to "the bot isn't receiving updates." To manually drive the live bot, run with `NODE_USE_ENV_PROXY=1` **and** temporarily pass `{ client: { fetch } }` to `new Bot(...)` in `bot.ts` (global `fetch` respects the env var) — revert that one-line override before committing, it's a sandbox-only workaround, not a real fix.
- Apps resolve `@ashena/db`/`@ashena/shared` via their built `dist/` output (package.json `main`/`types`), not TS source. Each package's own `typecheck` script uses `--noEmit`, so running `pnpm -r run typecheck` alone never produces that `dist/` — that's why the root `typecheck` script runs `build:packages` first. `pnpm build` doesn't need this: pnpm already runs `packages/*`'s `build` (which does emit) before `apps/*`'s in topological order.
- Prisma CLI (`migrate`/`validate`) only auto-loads a `.env` from the **same directory as `schema.prisma`**, not the repo root — `packages/db/.env` is a symlink to `../../.env` for this reason (gitignored either way).

## What this project is

**Ashenaiy (@ashenaiybot)** is a Telegram bot for anonymous chat with strangers, layered with a simplified Tinder-like flow: build a minimal profile, browse profile cards, Like/Pass, and on a mutual Like an anonymous chat opens — messages relay between the two users without ever exposing Telegram identity (username, numeric ID, phone number).

Two surfaces share one backend and one database:
1. **Bot-native mode** — entirely inline-keyboard driven inside Telegram chat.
2. **Mini App mode** — a Next.js + Geist web app launched from `/start`, offering richer UI (swipe cards, forms, settings) for the same underlying state.

A separate Next.js **Admin Panel** handles user management, report/ban moderation, and product metrics, with two roles: `admin` (full access) and `moderator` (report queue + temporary bans only).

## Architecture (implemented — EPIC 0/1/2/3/4)

**Monorepo layout** (plain pnpm workspaces, no Turborepo):
- `apps/bot-api` — Node.js + TypeScript backend: grammY bot layer (`src/bot.ts`, `src/bot/`), Fastify REST API (`src/server.ts`, `src/routes/v1/`), a BullMQ worker entrypoint (`src/worker.ts`) running two repeatable jobs (see Infra below). Service layer lives in `src/modules/{users,profiles,matching,chat,moderation,admin}/service.ts` — `users`, `profiles`, `matching`, `chat`, and `moderation` have real logic; `admin` is still an intentional empty stub (`export {}`) until EPIC 7. Bot handlers and REST routes both call the *same* service functions — no business logic embedded directly in a grammY handler or Fastify route, only orchestration. `src/bot/onboarding.ts` (EPIC 2) wires the full age-gate/gender/birth-date/bio/interests/photo flow plus profile editing; `src/bot/matching.ts` (EPIC 3) wires the candidate-browsing/swipe/preferences flow on top of it, registered after onboarding in `buildBot()` so its `callback_query:data`/`message:text` handlers pick up whatever onboarding.ts's handlers pass through via `next()` for data they don't recognize (`menu:find`, `swipe:*`, `pref:*`, etc.) — these two are unmodified from EPIC 2/3. `src/bot/chat.ts` (EPIC 4) wires the chat-relay/report/block flow and is registered **FIRST** in `buildBot()`, ahead of onboarding/matching — not registered last, deliberately: it claims an update only when the sender has an active `ChatSession` (or the update is one of its own self-contained `match:start:`/`report:`/`block:` callback prefixes), deferring everything else via `next()` to the untouched onboarding→matching chain. Registering it last was tried first and had a real bug (caught by adversarial review, see Progress below) — a stale onboarding `awaitingInput` edit-mode entry, or a message that happened to start with `/`, could hijack content meant for an active chat partner before chat.ts ever saw it; checking "does this user have an active chat" before any onboarding-state check runs at all closes that hole structurally. `src/bot/copy.ts` centralizes all Persian UX strings; `src/bot/keyboards.ts` builds the inline keyboards (interest/gender-preference multi-select state round-trips through the message's own keyboard, no server-side session for that), the swipe/match/preference/report/block callback-data parsers, and the one **reply keyboard** in the bot (`chatToolbarKeyboard()` — Telegram reply keyboards persist across messages, unlike inline keyboards, which is what "always available during an active chat" needs); `src/bot/awaitingInput.ts` is a single-instance, in-memory (not Redis) TTL map used only to disambiguate a free-text/photo reply during the optional/edit steps (onboarding's bio/interests/photo, and EPIC 3's age-range preference edit) — the required age/gender/birth-date steps are always resumable from persisted `User` fields alone via `deriveOnboardingStep()` in `modules/users/service.ts`, which is the single source of truth for "has this user finished required onboarding" — reuse it rather than re-deriving the same check.
- `apps/web-miniapp` — Next.js 15 App Router Mini App skeleton (hello-world page only so far). Real Telegram SDK integration, forms, and swipe deck are EPIC 6.
- `apps/web-admin` — Next.js 15 Admin Panel skeleton (hello-world page only so far). Real auth/moderation UI is EPIC 7.
- `packages/db` — Prisma schema (full EPIC 1 data model + EPIC 3's `MatchPreference` + EPIC 4/5's `BannedPattern`, see below) + a singleton `prisma` client. **Re-exports everything from `@prisma/client`** (`export * from "@prisma/client"` in `src/index.ts`) — other packages/apps import model/enum types from `@ashena/db`, never from `@prisma/client` directly, so this package stays the sole owner of the Prisma dependency. Also exports `canonicalUserPair()`, the single source of truth for the `Match.userAId`/`userBId` sorted-pair invariant (see below) — both the matching service and `prisma/seed.ts` import it rather than each having their own copy. `packages/db` depends on `@ashena/shared` (for the matching-preference default helpers seed data reuses) — a one-directional edge, `@ashena/shared` never depends back.
- `packages/shared` — `parseEnv()` helper (used by every backend env-loading module), `APP_NAME`, `src/onboarding.ts` (age/gender domain constants + pure helpers), `src/matching.ts` (EPIC 3 — default-preference computation, age-range parsing, birth-date-bounds-for-age-range math, all unit-tested against `calculateAge()` for consistency), `src/moderation.ts` (EPIC 4/5 — `ReportReasonValue`/`REPORT_REASON_OPTIONS`, mirroring `onboarding.ts`'s `GenderValue`/`GENDER_OPTIONS` pattern so the bot's report-reason keyboard and a future Admin Panel triage UI can't drift on the fixed reason list), and `src/api/*` — Zod request-validation schemas shared between `apps/bot-api`'s REST routes and (eventually) `apps/web-miniapp`'s forms, so validation can't drift between the bot and the Mini App for the same field (e.g. `upsertProfileSchema`).

**Auth plumbing (US-1.4)**: `apps/bot-api/src/lib/telegramInitData.ts` implements Telegram's official Mini App `initData` HMAC-SHA256 validation from scratch (no external validation package) — `secret_key = HMAC_SHA256(data=bot_token, key="WebAppData")`, `expected_hash = HMAC_SHA256(data=data_check_string, key=secret_key)`, timing-safe comparison, `auth_date` expiry check. `apps/bot-api/src/plugins/miniAppAuth.ts` wraps it as a Fastify preHandler (`x-telegram-init-data` header → 401 on anything invalid, else resolves/creates the `User` via `findOrCreateUserByTelegramId`). The bot side gets the same resolution via `apps/bot-api/src/bot/identityMiddleware.ts`, a grammY middleware setting `ctx.internalUser` (typed via the `BotContext` flavor in `bot/context.ts`) before any command handler runs.

**Matching engine (EPIC 3, `modules/matching/service.ts`)**: candidate selection (US-3.2) filters by mutual `MatchPreference` match (gender + age range, both directions), active status, block status in either direction, and a 30-day swipe cooldown — logic lives entirely in the service, not the bot handler. A per-user Redis list (`matching:queue:<userId>`) backs the browsing queue, refilled from Postgres under a short `SET NX PX`-based lock (`matching:refilling:<userId>`) so two concurrent refills (double-tap, two devices) can't both query the same batch and duplicate it. A Redis string (`matching:current:<userId>`, TTL-bound) tracks the last-delivered candidate as a cheap stale-tap guard in the bot handler, ahead of the real correctness guarantee: `SwipeAction` is *upserted* on the existing `@@unique([actorUserId, targetUserId])` constraint (US-3.3), so any number of double-taps collapse to one row regardless of timing. On a Like, a Postgres advisory lock (`pg_advisory_xact_lock`, keyed on the canonical user pair) serializes concurrent mutual-like races so exactly one side's call creates the `Match` and sends the (best-effort, retried) notifications — see `recordSwipeAndCheckMatch()`'s doc comment for the full race analysis. `MatchPreference` rows are created lazily with sensible defaults (opposite gender, own age ±5) the first time one is needed — from `sendMainMenu()` in `onboarding.ts` for the general case, and additionally right when required onboarding completes (the birth-date step) so a user is immediately visible as a candidate to others rather than waiting for them to reach the main menu.

**Chat relay + minimal safety (EPIC 4, `modules/chat/service.ts` + `modules/moderation/service.ts`)**: `ChatSession` start/resume/end lives in `chat/service.ts`; `moderation/service.ts` depends on it (report/block/ban all end a session as a side effect) — **one direction only**, `chat/service.ts` has no dependency back, so there's no import cycle; the bot layer (`bot/chat.ts`) is the orchestrator that calls `moderation.checkText()` before calling `chat`'s relay/persist functions, exactly like `bot/matching.ts` already orchestrates `recordSwipeAndCheckMatch()` + `notifyMatch()` as two separate calls rather than one service calling the other. A per-user Redis string (`chat:active:<userId>`, TTL-bound) is the fast-path "which session is this user in" pointer, mirroring EPIC 3's `matching:current:<userId>` pattern — Postgres remains the source of truth (a cache miss just costs one extra query and repopulates the pointer); clearing it on session-end is a compare-and-delete Lua script (`redis.eval`), not a plain `DEL`, specifically so ending one session can't wipe out a *different* session's legitimately-current pointer (a user can technically hold multiple simultaneously-active Matches/ChatSessions — nothing in EPIC 3 prevents it — though only the most-recently-opened one is what plain-text messages route to; this is a documented, deliberate simplification, not a multi-conversation inbox). `startOrResumeSession()` never duplicates a `ChatSession` for the same `Match` on a concurrent double-tap of "شروع گفتگو": it's wrapped in `pg_advisory_xact_lock(hashtext(matchId))`, the same technique (and same race class) as `recordSwipeAndCheckMatch()`'s mutual-like lock — and it refuses to start/resume at all if either party is no longer `active` (banned) or has blocked the other, so a stale match-found button can't bypass a block or reach a banned account. In-chat photos relay immediately (same as voice/stickers, via `file_id`, never `forwardMessage` — no sender metadata leaks) rather than being held for moderation: there's no NSFW classifier (EPIC 5) or manual review queue (EPIC 7) yet, so holding would mean photos never get delivered — a deliberate product decision, not an oversight, revisit once EPIC 5 ships a real classifier. The keyword filter (`moderation.checkText()`, minimal EPIC 5 slice for US-5.1) is a case-insensitive literal substring match against the DB-backed `BannedPattern` table (no regex engine exposed), cached in-process for 60s to keep Postgres off the per-message hot path; a matched message is blocked with the *same generic copy regardless of severity* (US-5.1's AC: don't help the sender learn what tripped the filter), and a `high`-severity match additionally auto-files a `Report` with `reporterId: null` (`Report.reporterId` is nullable specifically for this — a null reporter means "system-flagged by the keyword filter," distinguishing it from a user-submitted report). Report/Block/end-chat all use the *same neutral* "هم‌صحبتت از گفتگو خارج شد" copy toward the other party regardless of the real reason (never revealing a report/ban happened) — **block is the one exception**: it notifies the blocked party **not at all**, per US-4.6's AC. `moderation.banUser()`/`revertExpiredBans()` ship the full ban **mechanism** (BanRecord creation, enforcement via `identityMiddleware.ts` — see below — active-session termination, temporary-ban auto-expiry) but nothing in EPIC 4's user-facing flow calls `banUser()` yet; issuing a ban is EPIC 7's moderator UI, this is the enforced mechanism CLAUDE.md's hard-block requires, ready for EPIC 7 to call directly. `identityMiddleware.ts` (US-1.4) is also where every banned user is now short-circuited bot-wide (ban copy, no `next()`) — the single choke point every other module's handlers already run through.

**Infra**: single Docker Compose stack (`nginx`, `api`, `web-miniapp`, `web-admin`, `postgres`, `redis`, `worker`) on one VPS — `docker-compose.yml` for prod, `docker-compose.dev.yml` for local hot-reload dev (bind-mounts the repo over a `deps`-stage image, `tsx watch`/`next dev` as the command). Nginx (`nginx/`) does path routing (`/api/*`, `/`, `/admin/*`) and a baseline rate-limit zone over plain HTTP; the HTTPS server block is a template at `nginx/conf.d/ssl.conf.disabled` (rename once real certs exist at `nginx/certs/`, per the comments in `nginx/conf.d/default.conf`). Redis backs the matchmaking queue/current-candidate pointer/swipe-rate-limit counters (EPIC 3) and the chat active-session pointer (EPIC 4, see above); BullMQ (same Redis, a dedicated `ioredis` connection with `maxRetriesPerRequest: null`) runs two repeatable jobs from `worker.ts` — `idle-session-cleanup` (US-4.7, every 15 min, ends `ChatSession`s idle past `IDLE_SESSION_TIMEOUT_HOURS`) and `ban-expiry-sweep` (US-5.4, every 5 min, reverts expired temporary bans) — via a standalone grammY `Api` client (no polling; `bot.ts`'s `Bot` instance already owns polling in the main process, the worker must never also call `.start()`).

**Design system**: Geist (`geist` npm package for Sans/Mono fonts) + Tailwind CSS v4 + shadcn/ui themed on Geist tokens — not the archived `geist-ui` community package.

## Data model notes (`packages/db/prisma/schema.prisma`) — non-obvious decisions later epics must respect

- `User.gender`/`birthDate` are **nullable**, not required: `identityMiddleware`/`miniAppAuth` create a bare `User` row on first Telegram contact (US-1.4), before EPIC 2 onboarding has collected anything. Treat "onboarding complete" as "these plus `ageAttestedAt` are all non-null", not a separate boolean flag.
- `Match.userAId`/`userBId` must always be written as a **canonical (sorted) pair** — smaller id first — by whichever service creates the row. `canonicalUserPair()` (exported from `@ashena/db`, `packages/db/src/index.ts`) is the single source of truth for this ordering — both the matching service (`recordSwipeAndCheckMatch()`) and `packages/db/prisma/seed.ts` import and reuse it rather than each keeping a local copy. The `@@unique([userAId, userBId])` constraint only catches duplicate matches if this ordering is respected; Prisma can't express an unordered-pair constraint directly.
- `ChatSession` has both `endedReason` (enum: `user_ended` / `reported` / `blocked` / `banned` / `idle_timeout`) and a nullable `endedByUserId` — the latter is null for system-initiated endings (e.g. `idle_timeout`), so don't assume every ended session has an ending user.
- `SwipeAction` has `@@unique([actorUserId, targetUserId])` specifically so EPIC 3's double-tap idempotency (US-3.3) can rely on a DB constraint rather than app-level de-duping alone — `recordSwipeAndCheckMatch()` upserts on this key rather than inserting, so a double-tap (or a legitimate re-swipe after the 30-day cooldown) updates the existing row instead of erroring.
- `MatchPreference` is a **nullable one-to-one** on `User`, created lazily (not at onboarding time) with defaults computed from the user's own gender/birthDate — see the matching-engine paragraph above. `queryCandidateIds()`'s Prisma filter on this relation means a user with no `MatchPreference` row is invisible as a candidate to everyone; the two lazy-creation call sites (`sendMainMenu()` and the birth-date-onboarding-completion step) exist specifically to keep that window as small as possible.
- `Report.reason` is a closed enum matching EPIC 4's fixed reason list (harassment/unwanted_content/suspected_minor/spam/other) — extend the enum (a migration) rather than accepting free text if new reasons are needed.
- `Report.reporterId` is **nullable** — a null reporter means the keyword filter (US-5.1) auto-flagged the report, not a user; `fileReport()`/`hasFiledReportForSession()` in `modules/moderation/service.ts` both handle this.
- `BannedPattern` (EPIC 5, US-5.1 minimal slice) is a flat `pattern`/`severity` table, matched via case-insensitive literal substring — not a real profanity list, an illustrative starter seeded by `prisma/seed.ts`; editable without a deploy once EPIC 7's Admin Panel adds a UI over it.
- `Profile.photoUrl` stores a **Telegram `file_id`**, not an HTTPS URL (set in EPIC 2's bot photo-upload step) — same convention as `Message.contentRef`. Any epic that renders a profile photo (EPIC 3 swipe cards, EPIC 6 Mini App, EPIC 7 admin) needs to resolve it via the Bot API (e.g. `getFile`/`sendPhoto` with the file_id), not treat it as a directly loadable image URL. EPIC 3's candidate cards only show a photo when `photoModerationStatus === "approved"`.
- `Profile.interests` values are a **closed, shared list** — `INTEREST_OPTIONS`/`INTEREST_VALUES` in `packages/shared/src/onboarding.ts` — enforced by both the bot's inline keyboard and the REST API's Zod schema (`upsertProfileSchema`). Add new interests there (one edit, both surfaces pick it up), never allow free text.
- `Profile.photoSubmittedAt` (EPIC 5, US-5.2) is stamped automatically by `profiles/service.ts`'s `upsertProfile()` whenever `photoUrl` is part of the input — not by callers — so onboarding.ts's photo step and any future Mini App photo upload can't drift on this. Orders `listPendingPhotos()`'s manual review queue oldest-first; there is **no automated NSFW classifier** (a confirmed, deliberate product decision, not a gap — see PRD §12 and the Progress note above), so every uploaded photo waits here until EPIC 7 approves/rejects it.
- `Message.matchedPatternId` (EPIC 5, US-5.1) is nullable with `onDelete: SetNull` (not `Cascade`) — a historical flagged message must survive an admin later editing/deleting the `BannedPattern` that flagged it (EPIC 7's US-7.5), otherwise false-positive-rate review loses its own evidence the moment the offending pattern is fixed.
- `Report.resolvedAt`/`resolvedByAdminId`/`resolutionAction` (EPIC 5, US-5.3) are all set together by `resolveReport()` — never partially, `resolveReport()` guards against re-resolving an already-`actioned` report. `resolutionAction` is a closed enum (`no_action`/`warn`/`temporary_ban`/`permanent_ban`); the two ban actions compose directly with `banUser()` rather than duplicating ban logic.
- `BanAppeal` (EPIC 5, US-5.5) is **one-to-one with `BanRecord`** (`@unique banRecordId`) — this is what enforces "at most one appeal per ban" at the DB level (`submitBanAppeal()` throws on a duplicate; callers must check `hasAppealForBan()` first, same check-then-act idiom as `hasFiledReportForSession()`). A `reversed` appeal's `resolveBanAppeal()` reactivates the user (`status` back to `active`) **only if** the appeal's `BanRecord` is still that user's *current* ban (via `getLatestBanRecord()`) — a newer ban issued since the appeal was filed must not be silently lifted.

## Goals that should shape design decisions (§3)

- **G1 Activation**: ≥70% of users who send `/start` complete the minimal profile (gender, age range, 18+ attestation) in the same session — onboarding should be short and resumable, not a long form.
- **G2 Time-to-first-match**: target median under 5 minutes once supply is sufficient (no real baseline yet — post-launch data question).
- **G3 Safety SLA**: 95% of reports reviewed within 24h; high-severity reports (suspected minor, etc.) within 1h. This is why report severity/sorting (US-5.3) and immediate moderator surfacing of high-severity reports (US-4.5) are hard requirements, not nice-to-haves.
- **G4 Retention loop**: return-for-second-chat rate within 72h should be measurable (event tracking, Epic 8) even though there's no committed target yet.
- **G5 Dual-surface parity**: see constraints below — every Mini App action needs a bot-inline equivalent.

## Non-Goals for v1 — do not build these unless explicitly asked (§4)

- Monetization/payments (subscriptions, Boost, coins) — deferred to a separate spec.
- Live voice/video calls (no WebRTC infra).
- Native iOS/Android apps — bot + Telegram Mini App only.
- Mutual identity reveal — v2 feature (tracked as US-9.1 reference-only).
- Precise GPS-based matching — filters are gender/age range/(optional) language/interests only.
- Any platform besides Telegram (no WhatsApp/Instagram support).
- AI-generated ice-breakers/conversation starters — v2 (US-9.4 reference-only).

## Known risks & infra constraints (§9) — keep these in mind when choosing tools

- **Content/safety risk is critical-path**, not an add-on: photo/message abuse potential is why Epic 4 (chat relay) is hard-blocked on at least a minimal Epic 5 (keyword filter + ban) before real users touch it.
- **Self-attestation (18+) is insufficient alone** — it must be backed by a responsive report/moderation system; don't treat the age checkbox as sufficient compliance by itself.
- **Iran network access affects tooling choices**: GitHub, Sentry, and some CDNs can be intermittently restricted from Iranian IPs. This is *why* the stack deliberately avoids Sentry SaaS (uses self-hosted Pino + Prometheus + Grafana, with GlitchTip as a possible Sentry-alternative if needed) and why CI/CD platform was an open question (see Decisions log below).
- **Telegram Bot API connectivity** must be stable from wherever the server is hosted (Iran or otherwise) — flagged as a possible need for an outbound relay/proxy; not this project's problem to solve in code, but don't assume `api.telegram.org` is always trivially reachable.
- **Legal/regulatory risk** for an anonymous chat/dating-adjacent service under Iranian law is explicitly out of scope for product/engineering judgment — flagged for the user to get local legal advice on before public launch, not something to design around silently.

## Non-negotiable constraints when implementing any epic

- **Identity anonymity**: Telegram username, numeric ID, and phone number must never be shown to the other party in a match/chat. Bio/photo are not anonymous (visible by design); only Telegram-linked identity is protected.
- **Safety is not deferrable**: Report/Block/end-chat must ship *with* the chat relay (EPIC 4), not after it. Do not build chat relay without at least the baseline keyword filter + ban mechanism (minimal EPIC 5) before it's usable by real (non-internal-test) users.
- **Dual-surface parity**: every Mini App capability needs at least a simpler inline-keyboard equivalent in the bot, and both surfaces must read/write the same records (no divergent state or duplicated business logic per surface).
- **No raw age storage**: store `birthDate`, derive age at query time — never persist a stale computed age.
- **UX copy tone** (§8): CTAs start with a verb and state the concrete outcome; error messages state what happened + why + how to fix it, never raw technical/error codes; sensitive dialogs (ban, end chat, report) spell out consequences explicitly; the counterpart in chat is always called "هم‌صحبت" (never "پارتنر"/other variants); never imply to a user that their match might not be a real person.
- **Moderator vs admin**: banned-word list editing, broadcast sending, permanent-ban reversal, and user-record deletion are `admin`-only, not `moderator`.

An independent adversarial code-review pass on this diff (7 targeted angles, not a generic sweep) found one **confirmed** bug and three plausible hardening gaps, all fixed: (1) `checkSpamPattern()` was being called *before* `persistMessage()` in `bot/chat.ts`, so the message that actually crossed the 3-distinct-session threshold was never counted against itself — a user had to send a *4th* copy before the flag fired; fixed by persisting first. (2) `resolveBanAppeal()`'s `reversed` outcome didn't reactivate the user at all — fixed as described above.
